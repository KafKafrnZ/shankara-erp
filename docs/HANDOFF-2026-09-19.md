## 2. Date format in sheets

IT said dates still broke in places. That was real.

**What was wrong**

- Excel cells *typed* as Date were stored as `2024-01-15T00:00:00.000Z` (and `toISOString()` on IST midnight slipped back a day).
- Raw Excel serials (`45306`) only converted if the header matched `/date\|applicable\s*from/`. **Applicable To**, **W.E.F.**, **Valid From**, **As On**, **OB Date**, **Mfg Date**, **Expiry Date** were missed.

**What we did**

- Shared helper: `backend/src/common/sheet-date.ts`
  - Date-typed cells always become `YYYY-MM-DD` (column name does not matter).
  - Serials convert only on a date-looking header, so a 5-digit HSN/qty is not turned into a date.
  - Headers matched: `date`, `\bdt\b`, `w.e.f`, `applicable`, `valid from/to/till/until`, `as on`, `effective`, `period from/to`.
  - UTC-midnight `Date`s stay UTC. Anything else is a civil date in **Asia/Kolkata** — do **not** use `getFullYear()`/`getDate()` (that is what failed CI).
- Parser `unwrapCell` converts `Date` (and formula `result` Dates) via that helper instead of `toISOString()`.
- Tally export writes real Excel dates with `numFmt dd-mm-yyyy` on date columns.
- Frontend `formatSheetCell` shows `DD-MM-YYYY` and still repairs leftover serials/ISO strings already in `extra`.

**Tests:** `backend/src/common/sheet-date.spec.ts`, extra date rows in `item-master.parser.spec.ts`, one Tally-export case in `item-search.service.spec.ts`, `frontend/src/lib/format.test.ts`.

## 3. After Add item: new sheet vs existing live sheet

**Ask:** after filling the form or uploading Excel, ask whether to create a **new** live sheet (name it) or **add into an existing live sheet**.

**UI**

- `SheetDestination` (`frontend/src/components/SheetDestination.tsx`).
- Manual create: **Add item** → picker (not inside the field form, so Enter in the name field submits the picker).
- Upload: after the batch is `held`, **Add items** → same picker. Default new-sheet name is the uploaded filename without extension.
- New sheet name is required. Existing option lists `GET /api/meta/live-sources` and is disabled if none are live.

**API**

- `POST /api/item-batches/:id/publish` body (`PublishBatchDto`):
  - `{ destination: 'new', sheetName?: string }`
  - `{ destination: 'existing', targetBatchId: number }`
  - Empty body still means “publish as today” (keeps filename) — old e2e / clients.
- `POST /api/item-master/rows` accepts the same optional fields.

**How “existing sheet” is implemented (no migration)**

A live “sheet” is still a published `item_master_batch` that currently has live rows (`meta.service.ts` join).

On `destination: 'existing'`:

1. Publish as usual (close previous live versions of those `item_code`s).
2. Merge `extra_headers` onto the target batch.
3. `UPDATE item_master_row SET batch_id = target WHERE batch_id = this`.
4. The upload/manual batch stays `published` with **zero live rows**, so it disappears from the live-file pane.

On `destination: 'new'` with a name:

- If the batch has a `source_file`, rename `original_name`.
- If it is a manual batch (no file), insert a dummy `source_file` (`storage_key = manual/<sha>`, `byte_size = 0`) just to hold the display name. The live pane already reads `COALESCE(sf.original_name, 'Manual edit')`.

There is **no** `display_name` column.
